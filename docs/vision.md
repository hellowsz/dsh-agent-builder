# 设计说明

> 2026-08-18 已按飞书对齐稿的评论定稿,下面是拍板后的版本。

## 定位

面向**纯新手**,不用懂技术。yml 和 DeepSeek Harness 都是藏在后台的实现细节,用户只面对一件事:聊清要什么 → 拿到一个能稳定干活的 agent。

因为用户是纯新手、没法自己判断产出对错,"内容稳定"这件事比面向开发者时更吃重——产品价值几乎全压在"产出能不能被信任"上。

## 两种"稳定",别混

- **接线的稳定**:加载哪些插件、怎么注入、工具怎么挂,由 yml 声明,确定性路径,每次一致。底座直接提供。
- **内容的稳定**:模型每次产出的东西是否可靠。底座不提供,靠下面的验证机制压。

## 稳定性验证机制

- **多样例**:固化前必须跑一组覆盖不同输入的样例,不接受"跑通一次就固定"。
- **可检验的验收标准**:让"什么算合格"成为可判定条件(字段齐全、格式匹配、关键值命中),而不只是肉眼看一眼。
- **专属验证门禁**(核心设计,待专门调研):每个 agent 在固化时生成一套**为它定制的验证门禁**;运行时由门禁把关,不合格的产出不放行。门禁的具体形态、生成方式、运行时如何拦截,需要专门调研后再定。
- **诚实的稳定性报告**:固化前展示通过率和已知会翻车的情况,让用户在知情下决定要不要固定。

## 插件生态

- **独立仓库**:插件清单单独成一个仓库,作为**依赖 DeepSeek Harness 的生态仓库**,和本项目分开。
- **定时 agent 自动收集**:由一个独立的定时任务 agent **全网自动筛选**好用、高 star 的开源 DSH 相关插件并入库,不靠人工维护。
- **面向 AI 接入**:这份清单是给搭建助手(AI)挑选和接入用的,不是给人翻阅的目录。

## MVP 边界

- **首发场景待定**:先不锁死第一个做哪个任务,后续单独讨论再定。
- 先把一条链路打通并做到真的稳:聊清需求 → 选/装插件 → 跑多样例 → 出稳定性报告 → 用户确认 → 固定成 yml + 生成专属门禁 → DSH 里加载运行。
- 不追求"任意能力自由组合"。越通用越难兑现"稳定交付"的承诺。

## 待专门讨论

- **验证门禁怎么定制**:一个 agent 一套门禁的具体形态、生成方式、运行时拦截方式。
- **MVP 首发场景**:选哪个窄任务先跑通整条链。

## 最终架构定稿(2026-08-19,与实现对齐)

**设计与执行严格分离**:

- **agent builder(设计侧)只有两个能力**:①设计——把大白话需求编译成"拼接说明书"(spec + 门禁 + 提示词 + preset);②评审——DSH 拼出来的产物回到 builder,过确定性门禁复核 + ④独立评审。
- **DeepSeek Harness(执行侧)负责拼装**:候选配置挂载进真 DSH(headless),模型干活、门禁插件在 DSH 内实时 steer 把关;builder 绝不自己拼。
- **用户只做三次判断**:确认说明书 → 评估产物 → 定稿。样例由 AI 自造(可选补充真实样例),用户不出题。
- **资产库**:定稿产物(五件套)进用户资产,一键挂进 DSH 持续使用与交付。
- **双模式同能力**:网页向导(小白)与专业 CLI 共享同一任务库(sessions/)与资产库(agents/),任务持久化、随时恢复、跨模式接续。
- **第一性原则定位**:产品本质 = 把用户脑中模糊的"正确"编译成机器可判定的判据,再用拒绝采样强迫概率性生成通过它。价值沉淀在"被人类裁决背书过的判据"。已知待补:运行期翻车样本回流(判据飞轮)。
