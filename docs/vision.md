# 设计说明

## 定位取舍

产物是可自托管、可进版本库、可和真实代码拼装的 DSH 配置。吃这套价值的,主要是**想拥有运行时、不接受托管围墙的开发者和小团队**。纯新手不关心底座是什么,只认结果稳不稳。

当前锚定:**开发者与小团队自托管**这一侧。新手友好是后续目标,不在第一阶段承诺。

## 两种"稳定",别混

- **接线的稳定**:加载哪些插件、怎么注入、工具怎么挂,由 yml 声明,确定性路径,每次一致。底座直接提供。
- **内容的稳定**:模型每次产出的东西是否可靠。底座不提供,靠本项目的验证机制压。

对用户承诺的是第二种。所以"多样例测试 + 机械化验收 + 稳定性报告"是产品内核,不是附加功能。

## MVP 边界

第一阶段只做**一个窄场景**(输入输出都结构化的任务,例如按固定模板从原始资料里抽字段生成一份文档),把这条链路打通并做到真的稳:

对话收敛需求 → 选/装插件 → 跑一批多样化样例 → 出稳定性报告 → 用户确认 → 固定成 yml → DSH 里加载运行。

不追求"任意能力自由组合"。通用性是稳定性的敌人,越通用越难兑现"稳定交付"的承诺。

## 待验证的关键假设

- **插件生态是否够厚**:DSH 插件目前按模块路径/包解析,尚无成熟的插件市场。"去三方仓库找插件来组合"这句话背后,可能需要先自建常用插件(读表格、填模板、抓网页、发消息等)。这块隐藏成本要在 MVP 里摸清。见 `plugin-registry/README.md`。

## 稳定性验证机制(草案)

- **多样例**:固化前必须跑一组覆盖不同输入的样例,不接受"跑通一次就固定"。
- **可检验的验收标准**:让用户定义"什么算合格"的可判定条件(字段齐全、格式匹配、关键值命中),而不只是肉眼看一眼。
- **诚实的稳定性报告**:固化前展示通过率和已知会翻车的情况,让用户在知情下决定要不要固定。
- **线上护栏**:固化后运行时,输出格式校验、置信度不足转人工或重试、留可回放日志。
